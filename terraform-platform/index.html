Key engineering decisions

These are the choices that make the platform safe to change, cheap to run and easy to scale to new domains.

01

Modules vs domains

Blueprints in modules/ define how resources are built; domains/ only passes parameters. Standards live in one place and are never copy-pasted.

02

Blast-radius isolation

Every domain and environment has its own GCS state prefix. A change to Marketing can't touch Sales, and Dev can't touch Prod.

03

Dynamic CI/CD matrix

A discovery job scans domains/ at runtime and fans out one parallel job per stack. New domains are picked up with zero YAML changes.

04

Credential-free validation

CI runs fmt and validate with init -backend=false, so pull requests are checked without exposing any cloud credentials to the runner.

05

FinOps by design

cost_center and data_sensitivity are mandatory, validated inputs. Sandbox datasets get a 30-day table expiry automatically, so nothing is left running up storage.

06

Observability without the bill

Each dataset gets a log sink filtered to severity >= ERROR. Failures are always visible, while the flood of INFO logs never adds to logging costs.

07

Fault-tolerant streaming

Pub/Sub subscriptions route poison messages to a dead-letter queue after 5 attempts, and each domain gets its own Dataflow service account.

08

Scaffolding over copy-paste

A Jinja2 Cookiecutter template generates new domain stacks, choosing a Medallion or single-dataset pattern and optional streaming, so every domain starts compliant.

Engineered like a team repository

Built with the governance you'd expect in an enterprise platform team, not as a one-off script.
